# BusyMirror Roadmap

## Shipped (highlights)
- Route-driven mirroring (multi-source)
- Accepted-only filter (mirror your accepted meetings)
- Persistent settings with autosave/restore; Import/Export JSON
- Overlap modes (allow, skipCovered, fillGaps) and merge-gap
- Work Hours filter and title-based skip filters
- Privacy: placeholders with prefix + customizable title
- 1.3.0: Mark Private option (global + per-route) — **removed again in 1.5.0**, it never worked; see "Decided against"
- 1.3.4: persistent file logging, stale-calendar pruning on refresh, clickable top-bar mode toggle
- 1.3.6: in-app scheduling via `launchd` with hourly/daily/weekday modes
- 1.3.6: generated macOS app icon set and packaged release assets
- 1.4.0: unit-test suite (45 tests), Cancel button, progress indicator, sandbox LaunchAgent fix, mirror URL fix, engine refactor into `MirrorConfig`
- CLI diagnostics: `--help`, `--list-calendars [--json]`, `--status [--json]`, real exit codes (2 = no access, 3 = no saved routes), last-run tracking (time/ok/summary)
- 1.7.0: **Event-driven background sync**, replacing the hourly `launchd StartInterval` poll. Auto-sync logic lives in `BusyMirrorAppController` (an app-lifetime object, not tied to `ContentView`'s window lifecycle — closing the main window used to tear down the `EKEventStoreChanged` observer along with it, which would have made auto-sync a no-op whenever the window was closed). Once saved routes exist: registers as a login item (`SMAppService.mainApp`), removes any old `launchd` schedule, watches `EKEventStoreChanged` (debounced ~3s) and `NSWorkspace.didWakeNotification`, plus a 30-min fallback timer as a safety net. Auto-sync always writes (`writeEnabled: true`), independent of the interactive dry-run toggle.
- 1.8.0: **V2 UI polish.** `ContentView.swift` split from ~2000 lines into focused view files — `CalendarsSectionView`, `RoutesSectionView`, `ScheduleSectionView`, `LogSectionView` (state stays owned by `ContentView`/`@AppStorage`; these are view-layer extractions, not a full MVVM rewrite — the settings-persistence model didn't need touching and touching it is exactly how the 1.6.0/1.6.1 data-loss bug happened). A preferences window hosting the pure `@AppStorage`-backed defaults (time window, privacy/mirroring defaults, work hours, skip filters) that used to live in the main window; this surfaced a latent bug — moving fields out of `ContentView` meant they stopped re-triggering `saveSettingsToDefaults()`, so on next launch `applySnapshot` would have silently reverted a preference changed in the new window using the stale blob. Fixed by splitting launch-time restore (`restoreLaunchState`, routes/selections only, since @AppStorage fields already self-restore) from Import's full restore (`applySnapshot`, unchanged). Menu bar icon now reflects idle/syncing/error state, and the dropdown shows last-sync time/result and whether auto-sync is armed.
- 1.8.1: the preferences window (originally a `Settings{}` scene) didn't actually open — `LSUIElement` apps get no standard app menu, so Cmd+,/`SettingsLink` had no menu to hook into. Replaced with a plain `Window` opened via `openWindow(id:)`, plus a "Preferences…" menu bar item as a second entry point.
- 1.8.2: **standard app, not menu-bar-only.** Removed `LSUIElement` — Dock icon, Cmd+Tab, standard app menu (Cmd+Q) are back. The accessory-app design (no Dock icon) turned out to make the app hard to quit reliably, which blocked replacing the bundle during updates. Menu bar extra stays as a secondary quick-access point.
- 1.8.3: restored the real `Settings{}` scene for Preferences now that the app menu exists to host it (1.8.1's `Window`+`openWindow` workaround was never swapped back after 1.8.2 removed `LSUIElement`) — Cmd+, and the app's own "Preferences…" menu item work again, not just a button and a menu-bar-dropdown item.
- 1.9.0: **sidebar-navigation redesign** (Routes / Schedule / Activity Log via `NavigationSplitView`, toolbar actions, collapsed-by-default route list, structured log view, refreshed menu bar) — explored as a mockup first, direction confirmed before implementing. Also fixed a real bug the redesign work surfaced: routes were being silently dropped on most launches (a freshly-created `EKEventStore` right after a permission grant can under-report calendars for a moment, especially remote accounts, so pruning against it wrongly deleted routes referencing calendars that were actually still there) — only ever recovered by a legacy backup key that was itself frozen at its first-ever value. Fixed the prune timing and made the backup stay current.
- 1.10.0: **Developer ID signing + notarized release pipeline.** `DEVELOPMENT_TEAM`/hardened runtime set on the Release config; `make sign-app`/`notarize`/`package` sign with the Developer ID cert, submit to Apple's notary service, staple the ticket, then zip. Signing happens in a `/tmp` scratch dir, not in-repo — this repo lives under iCloud Drive, which re-tags every freshly written file with `com.apple.FinderInfo` before `codesign` can see it (reproduced with ditto, cp, and rsync alike), and `codesign` refuses to sign a bundle carrying that xattr.

## Next
1. **MCP server (thin external wrapper, not embedded in the app).** So agents driving BusyMirror don't have to shell out to the CLI and regex-parse log lines. A small standalone stdio-transport script (Node/Python) maps MCP tools 1:1 onto the CLI's `--json` output: `list_calendars`, `list_routes`, `run_route`, `run_saved_routes`, `get_status`. Deliberately kept out of the Swift app itself — no MCP SDK dependency in the signed binary (AGENTS.md's zero-external-packages rule stays intact), and MCP hosts spawn server processes on demand anyway, so there's no need for the app to run one persistently.
2. **Better server-side privacy mapping (per-provider heuristics).**
3. **iOS/iPadOS app — public App Store listing.** The app itself is done and shipping via TestFlight (see "iOS/iPadOS" below for full history). What's left is specifically the public-listing paperwork: privacy policy hosting, App Store screenshots per size class, privacy nutrition label (Calendar data, read+write, not linked/tracked), App Review notes/demo video justifying full calendar read/write access since there's no login flow to hand reviewers. None of this blocks TestFlight (internal or external) — only a full public App Store submission.

4. **Feature parity, macOS ↔ iOS.** Standing goal: a feature lands on both platforms in the same change unless the platform can't support it. The canonical status table and the user-facing behavior differences are in README.md ("macOS vs iOS"); update it as gaps close. Preview, per-route prefix mode, chained-mirroring toggles and the "has mirrors" tag are already at parity. The open gaps, in the order I'd do them:
   1. **iOS settings parity (one change, mostly plumbing).** Add to iOS Settings and thread through `RouteStore.run`/`preview` into `MirrorConfig`: sync window (days back/forward), editable placeholder title, auto-delete-missing toggle, Work Hours filter, accepted-only filter — all currently hardcoded in `RouteStore.run` (`1`/`14`, `"Busy"`, `false`/`false`/`true`). Small-to-medium: the engine already supports every one of them; it's UI + persistence keys (reuse the Mac's `@AppStorage` key names, as the prefix and skip filters already do). **Decision needed first:** the default window differs (Mac 7 days forward, iOS 14) — pick one for new installs; changing iOS's default alters what TestFlight testers' routes mirror. Note the placeholder title feeds mirror detection (`isMirrorEvent`'s title fallback) and Cleanup, so both must read the same value.
   2. **iOS defaults for new routes** (Private, Copy description, Sync reminders, All-day, Merge gap, Overlap — the form currently hardcodes Private on, everything else off/0/`allow`). Small; same shape as Mac's Preferences "defaults" section.
   3. **Mac App Intents (Shortcuts/Siri).** Mirror iOS's `RunAllRoutesIntent` / `RunRouteIntent` / `GetStatusIntent`. Medium: Mac has no `RouteStore` — routes live in `ContentView`'s `@AppStorage`/`SettingsPayload`, and headless running lives in `BusyMirrorAppController` (auto-sync, `MenuBarSupport.swift`) and the CLI path. The intents should call the same runner as auto-sync rather than a third copy, which probably means pulling that runner out of the controller first. The Mac target already has `GENERATE_INFOPLIST_FILE = YES`, so the App Intents metadata build step (the iOS gotcha) shouldn't bite.
   4. **iOS activity log.** Mac has a dedicated log view plus a rotating file; iOS shows only the last run's lines in the main list, though the shared `AppLogStore` (rotating file) already compiles into the iOS target and just isn't used by `RouteStore`. Append engine output there and add an Activity screen. Small-to-medium.
   5. **Import/Export settings — open question, not a plan.** Mac's is a same-machine backup (calendar identifiers are local to a device's calendar database, so exported routes generally won't resolve on another device). An iOS copy of that is low value. The genuinely useful version is *cross-device* route transfer (Mac → iPhone), which needs matching calendars by title + account instead of identifier — a real design task with ambiguity handling (duplicate names), and it edges toward the "no sync between apps" decision. Decide whether it's wanted before building anything.
   6. **Process:** when a feature is built on one platform, either build the other side in the same change or record the gap in README's table with the reason. The iOS-first features that were left as "Mac UI is a follow-up" are exactly what this rule is meant to prevent.
   Platform-inherent differences, deliberately *not* gaps: CLI, `launchd` scheduling, menu bar and event-driven auto-sync are Mac-only; `BGAppRefreshTask` best-effort sync is iOS-only; manual source/target selection is Mac-only (iOS is routes-only); Mac's Dry Run toggle has no iOS counterpart (Preview covers it).

Safe to do because the loop-guard (`isMirrorEvent` in `MirrorUtils.swift`) checks the `mirror://...` URL tag *first* and short-circuits before ever looking at the title prefix — the prefix is cosmetic/display-only, not load-bearing for detection, so per-route values can't break re-mirror protection. Only iOS got the UI (`RouteFormView`'s new "Prefix override" field, defaulting to blank = inherit); (Mac's route cards got the same control later — see the Mac parity entry below.)
- **Cross-device "already mirrored" detection.** Since every mirror event carries that same `mirror://` URL tag regardless of which app/device/prefix wrote it, `RouteStore.calendarsContainingMirrors(_:)` can flag calendars that already contain mirrored events without needing to know anything about the other device's routes or prefix — genuinely useful now that Mac and iOS have separate, unsynced calendar sets (per the earlier "standalone app" decision) and it's easy to accidentally pick an already-mirrored-into calendar as a new source. Shown as a badge next to the calendar in the source/target pickers and on route rows. Enables deliberate chained mirroring (A → B on one device, B → C on another) which the loop-guard would otherwise always block. Wired through all 4 `MirrorConfig` construction sites: Mac's auto-sync (`MenuBarSupport.swift`), Mac's route runner and manual-selection mode (`ContentView.swift`, the latter hardcoded false — no per-route concept there), and iOS's `RouteStore.run`. iOS got the UI (`RouteFormView` toggle with an explicit footer warning: don't enable on a route that loops back to its own target, or every run duplicates events further). (Mac's route cards got the toggle later — see the Mac parity entry below.)
- **Per-route "copy chained titles as-is" toggle**, fixing the prefix-stacking problem the toggle above introduces (e.g. `B: A: Meeting`). Only shown/meaningful when "Mirror already-mirrored events" is on. Implementation needed no new marker character — the existing `mirror://` URL tag (already used by `isMirrorEvent`) reliably identifies a source event as itself a mirror, so that same check (computed once at read time in `MirrorEngine.swift`) is now captured onto a new `Block.isMirrorSource` flag and consulted again at title-build time (`MirrorEngine.swift:~382`). Note the merge path (`mergeGapMin > 0`) already discards per-event titles/labels (pre-existing behavior, see the `ponytail:` comment in `BlockMath.swift`) — the same applies to this flag, so pass-through is only meaningful in per-event mode.
- **Fix:** the above initially let pass-through bypass a route's own Privacy setting for chained events. Gated on `!config.hideDetails` — Privacy now always wins, falling back to the normal prefix+placeholder path regardless of pass-through.
- **Per-route prefix mode: Global / Custom / None**, replacing the plain "Prefix override" text field. `Route.titlePrefix: String?` already structurally supported three states (`nil` = inherit global, `""` = no prefix, non-empty = custom) since the engine already no-ops on an empty prefix everywhere — the only real gap was the UI conflating "field left blank" with "inherit," leaving no way to explicitly pick "no prefix at all" per route. Confirmed necessary (not just theoretical) by a real multi-hop scenario: same source calendar mirrored to one target wanting a matching custom prefix, another wanting the global default, another wanting no prefix at all — and verified the per-event `isMirrorSource` split already handles a source calendar mixing tagged-chain events with genuine untagged ones correctly with zero extra config (each event classified individually at read time, not per-calendar).
- **The marker character came back, for a narrower reason than first proposed.** The toggles above didn't cover one case: under Privacy, a chained route couldn't preserve the *upstream* prefix (e.g. `WORK1: Busy`) while still using its own prefix for genuinely native events on the same source calendar (`WORK: Busy`) — Privacy forces `config.titlePrefix + placeholderTitle` uniformly, never consulting the upstream title at all. Added `mirrorTitleMarker` (`MirrorUtils.swift`, U+2063 invisible separator) embedded right after a route's own prefix on every newly-built title, plus `extractMirrorPrefix(from:)` to recover just the upstream prefix from it. `passThroughMirroredTitles` now has two paths: Privacy off → relay the upstream title completely verbatim (marker included, so a third hop can still extract from it — chains of 3+ are supported for free); Privacy on → keep the upstream's extracted prefix but substitute this route's own placeholder, falling back to this route's own prefix if no marker is found (pre-marker/legacy events). Unit-tested (`MirrorUtilsTests`, 4 new cases). Already-created events will get the marker added on their next resync (one-time title diff, self-healing, not a bug).
- **Preview (iOS), replacing the idea of a dry-run mode.** iOS had no dry-run at all — every Run wrote to real calendars immediately — and Mac's dry-run is log lines nobody would scroll through on a phone. Instead of a mode toggle (state people forget), there's now a **Preview** button in the route add/edit form, working on the *unsaved* form state, plus a Preview entry in a saved route's ⋯ menu. Engine side: `MirrorEngine.onPlannedChange` emits a `PlannedChange` at each of the five `WOULD ...` sites (dry-run only; Mac unchanged apart from the fidelity fixes below); `needsUpdate` → `updateReasons` so updates say *why* (a title differing only by the invisible chain marker gets its own reason — otherwise the first resync after the marker rollout would show many updates with visually identical titles). Two dry-run fidelity fixes found while reading the engine, which also make Mac's dry-run log more accurate: dry-run now extends `occupied` and records the time key after each would-be create/update like a real run does (previously `skipCovered`/`fillGaps` and identical-time source events would preview changes a real run skips), and dry-run increments the create counter like it already did the update counter (summary line said `created=0`). Deliberately *not* done: Apply executing the exact previewed plan (would need splitting the engine into plan/execute phases — Preview is a snapshot of right now), and forced-preview-on-first-run (the in-form button covers new routes). Pure pieces (`PlannedChange.swift`: grouping, summary, title-reason, extra notes) have 13 unit tests; the SwiftUI sheet and the dry-run-vs-real equivalence were verified by build and code reading only, not exercised against real calendars (no simulator on this machine).

Added `RouteCodingTests` (legacy JSON without the newer keys still decodes; `""` stays distinct from `nil` through JSON) since Mac persists routes as JSON and this repo has a history of route-loss bugs. ## Decided against
- **Direct Google/CalDAV/Exchange API integration** (OAuth flows, token storage, per-provider clients so BusyMirror can mirror a non-local calendar without it being added to macOS). EventKit already surfaces any calendar added via System Settings → Internet Accounts — macOS does the sync, auth, and refresh. Building a parallel integration would duplicate the OS for the narrow case of an account that can't or won't be added system-wide (e.g. MDM-restricted work accounts). Not worth the OAuth/Keychain/per-provider-quirk surface for that.
- **"Mark Private" — flagging mirrored events as private on the calendar server.** Shipped in 1.3.0, removed in 1.5.0. EventKit has no public API for it (the SDK's `EKEvent`/`EKCalendarItem` headers contain nothing for privacy, classification or sensitivity — re-checked against the current SDK), so the feature was built on an Objective-C runtime hack (`setPrivate:`, KVC on `sensitivity`/`classification`) that never worked reliably and would have blocked App Store review. The README kept advertising it for years after removal; that is fixed. Privacy is done client-side instead: Private mode mirrors a placeholder title with no notes.
